Docker مشکل «بسته‌بندی» را حل کرد؛ اما وقتی ده‌ها کانتینر روی چند سرور دارید، سؤال‌های تازه پیدا می‌شود: اگر یک کانتینر مرد، چه کسی دوباره بالا بیاوردش؟ ترافیک بین نسخه‌ها چطور تقسیم شود؟ ارتقای نسخه بدون قطعی چطور انجام شود؟ **Kubernetes** (K8s) سیستم ارکستراسیون کانتینرهاست که این‌ها را خودکار می‌کند و امروز استاندارد فی الواقع صنعت است — مدرک CKA هم معتبرترین مدرک این حوزه است.

## Kubernetes دقیقاً چه مسئولیت‌هایی می‌پذیرد؟

کلاستر K8s یک «سیستم‌عامل برای دیتاسنتر» است. شما **حالت مطلوب (Desired State)** را تعریف می‌کنید — «همیشه ۳ نسخه از این سرویس در حال اجرا باشد» — و K8s بی‌وقفه واقعیت را با آن مقایسه و اصلاح می‌کند. این حلقه آشتی (Reconciliation) قلب همه‌چیز است:

- **خودترمیمی:** کانتینری که کرش کند، خودکار جایگزین می‌شود.
- **مقیاس‌پذیری:** تعداد نسخه‌ها با یک دستور (یا خودکار با متریک) بالا و پایین می‌رود.
- **انتشار بدون قطعی:** نسخه جدید مرحله‌به‌مرحله جایگزین می‌شود و اگر سلامت نبود، برگشت خودکار.
- **کشف سرویس و متعادل‌سازی بار:** سرویس‌ها با نام همدیگر را پیدا می‌کنند و ترافیک تقسیم می‌شود.

## معماری کلاستر

کلاستر از دو نوع گره تشکیل می‌شود:

- **Control Plane (مدیریت):** مغز تصمیم‌گیری. اجزای اصلی: **API Server** (تنها نقطه ورود همه دستورها)، **etcd** (دیتابیس وضعیت)، **Scheduler** (تصمیم اینکه هر Pod کدام Node برود) و **Controller Manager** (اجرای حلقه‌های آشتی).
- **Worker Nodes (اجرا):** جایی که بار واقعی می‌چرخد؛ شامل **kubelet** (گویا با API Server و اجرای Podها) و **Container Runtime** (مثل containerd).

نکته امنیتی مهم: همه‌چیز از API Server رد می‌شود؛ دسترسی به آن یعنی دسترسی به کل کلاستر. همین‌جا مفهوم **RBAC** (کنترل دسترسی نقش‌محور) وارد می‌شود که در آزمون CKA سهم جدی دارد.

## Pod، Deployment، Service؛ سه‌گانه هر روز

**Pod** کوچک‌ترین واحد استقرار است: یک یا چند کانتینر که با هم مستقر می‌شوند و IP مشترک دارند. Podها فانی‌اند؛ با هر بازنشر، IP عوض می‌شود. پس مستقیم با Pod کار نمی‌کنیم — با دو منبع بالاتر کار می‌کنیم:

**Deployment** مدیریت نسخه‌های یک اپ را می‌پذیرد: تعداد نسخه (Replica)، استراتژی به‌روزرسانی و پروب‌های سلامت:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: shabamouz-web:1.0
          ports:
            - containerPort: 3000
          readinessProbe:
            httpGet:
              path: /healthz
              port: 3000
```

**Service** یک IP و DNS پایدار جلوی Podهای متغیر می‌گذارد. انواع رایج: `ClusterIP` (داخل کلاستر — پیش‌فرض)، `NodePort` (باز کردن پورت روی هر Node) و `LoadBalancer` (درخواست LB واقعی از ابر):

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 3000
  type: ClusterIP
```

ترافیک ورودی وب معمولاً بعداً با **Ingress** (قواعد HTTP/دامنه) مدیریت می‌شود؛ Service لایه‌ای است که Ingress به آن ختم می‌شود.

## kubectl؛ ابزار روزمره

این شش دستور ۹۰٪ کار روزانه را پوشش می‌دهند:

```bash
kubectl get pods -o wide          # وضعیت Podها و Node میزبان
kubectl get deploy,svc            # خلاصه Deployment و Serviceها
kubectl apply -f deploy.yaml      # اعمال/به‌روزرسانی منابع از فایل
kubectl logs deploy/web -f        # لاگ زنده همه نسخه‌های web
kubectl scale deploy web --replicas=5
kubectl rollout undo deploy/web   # بازگشت به نسخه قبلی
```

دو سطر آخر را در ذهنتان به K8s دیکته کنید: `scale` یعنی «حالت مطلوب را عوض کن» و K8s بقیه را می‌چیند؛ `rollout undo` یعنی بازگشت بی‌دردسر به انتشار قبلی — همان چیزی که در قدیم شبانه‌روزی طول می‌کشید.

## ConfigMap و Secret؛ پیکربندی جدا از ایمیج

یک ایمیج باید در همه محیط‌ها (تست، عملیات) یکسان باشد؛ تفاوت‌ها — آدرس دیتابیس، کلیدها — بیرون ایمیج می‌روند:

- **ConfigMap:** پیکربندی غیرمحرمانه (نام هاست، فلاگ‌ها) که به‌شکل متغیر محیطی یا فایل به Pod تزریق می‌شود.
- **Secret:** همان الگو برای داده‌های حساس؛ به‌صورت base64 ذخیره می‌شود و در APIServer کنترل دسترسی جداتری دارد. رمزگذاری در حالت سکون (Encryption at Rest) و یکپارچگی با Vault موضوع سطح بعدی است.

## جمع‌بندی

- Kubernetes حالت مطلوب را با حلقه آشتی محقق نگه می‌دارد: خودترمیمی، مقیاس و انتشار بدون قطعی.
- Control Plane تصمیم می‌گیرد (API Server، etcd، Scheduler) و Workerها اجرا می‌کنند (kubelet، runtime).
- Pod فانی است؛ Deployment تعداد و سلامت نسخه‌ها را می‌سازد و Service آدرس پایدار می‌دهد.
- kubectl ابزار روزمره است؛ scale و rollout undo دو دستوری هستند که ارزش K8s را نشان می‌دهند.
- پیکربندی و رمزها با ConfigMap و Secret از ایمیج جدا می‌شوند.

برای تمرین: با minikube یا kind یک کلاستر تک‌گره بالا بیاورید، همین Deployment و Service را اعمال کنید و سه آزمایش بکنید: یک Pod را حذف کنید (خودترمیمی)، replicas را به ۵ برسانید و نسخه ایمیج را به یک تگ اشتباه عوض کنید تا ببینید readinessProbe و rollout چطور عمل می‌کنند.
