وقتی اینترنت قطع می‌شود، فهمیدن اینکه «مشکل کجاست» مهارت واقعی یک کاربر حرفه‌ای است. خبر خوب این است که سه ابزار ساده در ویندوز تقریباً همه مسیر عیب‌یابی را پوشش می‌دهند: `ping`، `tracert` و `nslookup`. در این درس یاد می‌گیرید با روندی منظم مشخص کنید مشکل از کابل است، از IP، از DNS یا از سرور مقصد.

## روند طلایی عیب‌یابی

قبل از اجرای هر دستوری، این منطق را در ذهنتان بچینید: از نزدیک‌ترین نقطه به دستگاه شروع کنید و قدم‌به‌قدم دورتر شوید. هر قدم که جواب داد، مشکل را از آن نقطه به بعد حذف می‌کنید:

1. پیکربندی IP خودتان را ببینید: آیا اصلاً آدرس دارید؟ (`ipconfig`)
2. با گیت‌وی محلی ارتباط بگیرید: آیا تا روتر راه هست؟ (`ping` به IP گیت‌وی)
3. با یک IP معروف ولی بدون نام تست کنید: آیا اینترنت دارید؟ (`ping 8.8.8.8`)
4. با نام دامنه تست کنید: آیا DNS سالم است؟ (`ping google.com`)
5. اگر تا اینجا همه چیز خوب بود و فقط یک سایت باز نمی‌شود، مشکل از آن سرور است، نه شما.

## دستور ping؛ کنجکاوترین دوست شما

`ping` یک بسته کوچک به مقصد می‌فرستد و منتظر پاسخ می‌ماند؛ مثل صدا زدن «بخوابی؟» در تاریکی. اگر پاسخ آمد، اتصال تا آن نقطه سالم است:

```
ping google.com
```

خروجی معمول شبیه این است:

```
Pinging google.com [142.250.185.78] with 32 bytes of data:
Reply from 142.250.185.78: bytes=32 time=12ms TTL=118
Reply from 142.250.185.78: bytes=32 time=11ms TTL=118
```

سه عدد مهم در این خروجی:

- **time:** زمان رفت‌وبرگشت بسته برحسب میلی‌ثانیه؛ هرچه کمتر، بهتر. بازی‌های آنلاین معمولاً کمتر از ۵۰ میلی‌ثانیه می‌خواهند.
- **TTL:** تعداد هاپ (پرش بین روترها) باقی‌مانده تا پایان عمر بسته. هر روتر یک واحد کم می‌کند؛ از آن می‌شود حدس زد چند سیستم در راه بوده‌اند.
- **Request timed out:** مقصد یا یکی از روترهای مسیر پاسخ نداد؛ علامت زنگ خطر.

دو پارامتر پرکاربرد:

```
ping -t google.com      به‌صورت پیوسته تست می‌کند (با Ctrl+C متوقف شود)
ping -n 4 google.com    دقیقاً ۴ بسته می‌فرستد (پیش‌فرض ویندوز همین است)
```

## tracert؛ دیدن مسیر

وقتی ping شکست می‌خورد، مهم است بدانید **کجا** شکست خورد. `tracert` بسته‌هایی با TTLهای افزایشی می‌فرستد تا تمام روترهای مسیر را یکی‌یکی آشکار کند:

```
tracert google.com
```

```
  1     1 ms     1 ms     1 ms   192.168.1.1
  2     8 ms     9 ms     8 ms   85-15-20-1.isp.net
  3    12 ms    12 ms    13 ms   core1.isp.net
  4    *        *        *       Request timed out.
```

خواندن خروجی ساده است: هر سطر یک روتر در مسیر است. اگر از سطری به بعد فقط ستاره ببینید، ارتباط در همان نقطه قطع شده یا آن روتر اجازه پاسخ نمی‌دهد. سطر اول معمولاً روتر خودتان است؛ اگر همین سطر اول از کار بیفتد، مشکل داخل خانه شماست.

## nslookup؛ تست مستقیم DNS

اگر ping به IP جواب می‌دهد ولی ping به نام دامنه نه، مشکل تقریباً همیشه در DNS است. با `nslookup` جدا از ping می‌توانید مستقیم از سرور DNS بپرسید:

```
nslookup google.com
```

```
Server:  dns.isp.net
Address:  85.15.1.2

Non-authoritative answer:
Name:    google.com
Address:  142.250.185.78
```

اگر این دستور خطا بدهد ولی اینترنت IP-محور کار کند، سرور DNS شما مشکل دارد؛ می‌توانید موقتاً از DNS عمومی مثل `8.8.8.8` استفاده کنید یا cache را با `ipconfig /flushdns` پاک کنید.

## جمع‌بندی

- روند عیب‌یابی از نزدیک به دور است: IP خودتان، گیت‌وی، یک IP خارجی، سپس نام دامنه.
- ping دسترسی و تأخیر را می‌سنجد؛ time یعنی زمان رفت‌وبرگشت و TTL یعنی هاپ باقی‌مانده.
- tracert نشان می‌دهد بسته از کدام روترها عبور می‌کند و قطعی دقیقاً در کدام نقطه است.
- nslookup تنها ابزار تست مستقیم ترجمه نام به IP است و مرز بین «مشکل DNS» و «مشکل مسیر» را مشخص می‌کند.

برای تمرین: همین حالا سه دستور این درس را اجرا کنید و خروجی هر کدام را با متن بالا مقایسه کنید. در ترمینال شبیه‌سازی‌شده شب‌آموز هم می‌توانید بدون ریسک این دستورها را امتحان کنید.
