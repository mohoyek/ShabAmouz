سرویسی که تاکنون ساختید، روی کدام زیرساخت است؟ اگر جواب «سروری که یک بار با پنل وب ساختیم و کسی یادش نیست» باشد، زیرساخت شما خطرناک‌تر از کد بدون گیت است: بدون تاریخچه، بدون بازگشت و بدون تکرارپذیری. **Infrastructure as Code (IaC)** زیرساخت را مثل نرم‌افزار مدیریت می‌کند — در فایل، در گیت، با بازبینی — و **Terraform** پرکاربردترین ابزار این حوزه است (مدرک Terraform Associate هم مدارک استاندارد همین ابزار است).

## IaC چه مسائلی را حل می‌کند؟

- **تکرارپذیری:** یک تعریف، استقرار یکسان در آزمایشگاه و عملیات. «روی سیستم من کار می‌کرد» در سطح زیرساخت یعنی «در محیط تست بود ولی production فرق داشت» — IaC این شکاف را می‌بندد.
- **مستندسازی زنده:** فایل‌های Terraform دقیقاً توصیف می‌کنند چه چیزی وجود دارد؛ هیچ دیاگرامی از تاریخ نمی‌ماند.
- **بازبینی تغییرات:** تغییر زیرساخت مثل تغییر کد از Pull Request رد می‌شود؛ `terraform plan` قبل از merge نشان می‌دهد دقیقاً چه ساخته و چه نابود می‌شود.
- **بازیابی از بحران:** کل زیرساخت در چند دقیقه از کد بازساخته می‌شود — شما در «مدیریت رخداد» به این قدرت نیاز خواهید داشت.

## ساختار کد و چرخه کاری

Terraform زبان **HCL** دارد و منطق کارش «تعریف حالت مطلوب» است: می‌گویید چه چیزی باید وجود داشته باشد؛ خودش ترتیب ساخت را می‌فهمد:

```hcl
terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.0"
    }
  }
}

resource "docker_image" "web" {
  name = "ghcr.io/acme/web:1.4.2"
}

resource "docker_container" "web" {
  name  = "web"
  image = docker_image.web.image_id
  ports {
    internal = 3000
    external = 8080
  }
}
```

این نمونه با پرووایدر Docker کار می‌کند و روی هر سیستم آزمایشگاهی بدون ابر اجرا می‌شود؛ در کار واقعی، پرووایدرهای AWS/Azure/GCP یا حتی DNS و گیت‌هاب جای آن می‌نشینند و همان نحو کار می‌کند. چرخه کاری همیشه سه مرحله دارد:

```bash
terraform init     # دانلود پرووایدرها؛ یک بار برای هر پوشه
terraform plan     # پیش‌نمایش تغییرات: +ساخت ~تغییر -حذف (هیچ‌چیز عوض نمی‌شود)
terraform apply    # اعمال واقعی پس از تأیید
```

عادت حرفه‌ای: `plan` هرگز مستقیماً اجرا نمی‌شود؛ همیشه در PR بازبینی می‌شود و خروجی‌اش به کد پیوست است. `apply` بدون دیدن plan قبلی، قمار است.

## State؛ مهم‌ترین نقطه خطر Terraform

Terraform برای اینکه بداند «واقعیت الان چیست»، آن را در فایلی به نام **State** نگه می‌دارد — شامل حتی اطلاعات حساس. سه قانون بی‌چون‌وچرا:

1. **State را در گیت کامیت نکنید** (شامل رمز است و هم‌زمان دو نفر می‌شکنندش).
2. **State اشتراکی و راه‌دور:** در تیم از Backend راه‌دور (S3، Azure Blob، یا Consul) با قفل‌گذاری (Locking) استفاده کنید تا دو اجرای هم‌زمان، زیرساخت را خراب نکند.
3. **پشتیبان‌گیری State:** از دست دادن State یعنی Terraform رابطه‌اش با منابع واقعی را می‌بازد؛ پشتیبانِ خودکار Backend اجباری است.

```hcl
terraform {
  backend "s3" {
    bucket = "acme-tfstate"
    key    = "prod/web/terraform.tfstate"
    region = "eu-central-1"
  }
}
```

## ماژول‌ها؛ ترکیب‌پذیری زیرساخت

وقتی الگوی «وب + دیتابیس + شبکه» را دوبار لازم داشتید، آن را در یک **ماژول** بسته‌بندی می‌کنید — تابعِ زیرساخت با ورودی و خروجی:

```hcl
module "web_prod" {
  source      = "./modules/web-service"
  environment = "production"
  replicas    = 3
  domain      = "shabamouz.example.com"
}
```

سه قاعده طراحی ماژول: هر ماژول یک مسئولیت؛ ورودی‌ها با `variable` و خروجی‌ها با `output` تعریف می‌شوند؛ نسخه‌گذاری ماژول‌های اشتراکی با تگ گیت انجام می‌شود. کتابخانه ماژول‌های داخلی، ارثیه واقعی یک تیم DevOps است.

## IaC در ستون DevSecOps

زیرساخت در کد یعنی سیاست‌های امنیتی هم کد می‌شوند: اسکن `plan` با ابزارهایی مثل Checkov یا tfsec در پایپ‌لاین، جریمه سطل‌های عمومی یا پورت‌های باز را قبل از اجرا می‌گیرد. این دقیقاً هم‌راستای «DevSecOps» است که در نقشه راه همین سطح به آن اشاره شد: امنیت به‌صورت خودکار و در مسیر تغییر، نه بازرسی دستی بعدی.

## جمع‌بندی

- IaC زیرساخت را تکرارپذیر، مستند و بازبینی‌پذیر می‌کند؛ Terraform با HCL «حالت مطلوب» را تعریف می‌کند.
- چرخه کاری init → plan → apply است و plan در PR بازبینی می‌شود؛ apply بدون plan قمار است.
- State مغز Terraform است: راه‌دور، قفل‌دار، پشتیبان‌گرفته و هرگز داخل گیت.
- ماژول‌ها الگوهای تکرارشونده را با variable/output بسته‌بندی می‌کنند.
- با اسکن IaC در پایپ‌لاین، امنیت زیرساخت هم خودکار و پیشگیرانه می‌شود.

برای تمرین: همین کد Docker را اجرا کنید؛ سپس پورت را عوض کنید و خروجی `plan` را بخوانید — ببینید Terraform چطور «تغییر» را توصیف می‌کند. بعد یک resource را از کد حذف و بدون apply آن را دستی پاک کنید و ببینید plan چه می‌گوید؛ این آزمایش فهم State را محکم می‌کند.
