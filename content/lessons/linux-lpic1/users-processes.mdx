یک ادمین لینوکس هر روز دو کار تکراری دارد: مدیریت کاربران و مدیریت سرویس‌ها. وقتی برنامه‌ای کند شده، باید بفهمید کدام فرآیند مقصر است؛ وقتی همکار جدید وارد تیم می‌شود، باید حساب کاربری با مجوز درست بسازید. این درس پایانی مسیر LPIC-1 این دو مهارت را پوشش می‌دهد و با systemd — قلب مدرن مدیریت سرویس‌ها — تمام می‌شود.

## کاربران و گروه‌ها

هر کاربر در لینوکس یک شناسه عددی (**UID**) دارد؛ root همیشه UID=0 است. اطلاعات کاربران در سه فایل کلیدی نگهداری می‌شود:

| فایل | محتوا | نکته آزمون |
|---|---|---|
| `/etc/passwd` | نام، UID، GID، دکمه، پوسته | برای همه قابل خواندن؛ رمز واقعی ندارد |
| `/etc/shadow` | هش رمزها و سیاست انقضا | فقط root می‌خواند |
| `/etc/group` | گروه‌ها و اعضا | عضویت مکمل کاربر |

```bash
useradd -m -s /bin/bash reza    # ساخت کاربر با دکمه و پوسته
passwd reza                     # تعیین رمز
usermod -aG docker reza         # افزودن به گروه docker (-aG یادتون نره!)
id reza                         # دیدن UID و گروه‌های کاربر
groupadd developers             # ساخت گروه
deluser --remove-home reza      # حذف کاربر و دکمه‌اش
```

**هشدار رایج:** `usermod -G` بدون `-a` گروه‌های قبلی را پاک می‌کند و عضویت‌های مهم (مثل sudo یا docker) را از بین می‌برد؛ این یکی از سؤال‌های محبوب آزمون و یکی از اشتباهات واقعی ادمین‌هاست.

**sudo** اجازه اجرای دستور مدیریتی را می‌دهد. سیاست‌ها در `/etc/sudoers` و ترجیحاً فایل‌های `/etc/sudoers.d/` تعریف می‌شوند و ویرایش آن‌ها فقط با `visudo` انجام می‌شود (چون قبل از ذخیره معتبربودن را چک می‌کند):

```sudoers
reza     ALL=(ALL:ALL) ALL          # دسترسی کامل با رمز
%devops  ALL=(ALL) NOPASSWD: ALL    # گروه devops بدون رمز
```

## فرآیندها و سیگنال‌ها

هر برنامه در حال اجرا یک **فرآیند (Process)** با شناسه **PID** است. فرآیند اول سیستم، init/systemd با PID=1 است و درخت همه فرآیندها از آن می‌روید.

```bash
ps aux                # همه فرآیندها با جزئیات
ps -ef | grep nginx   # جستجوی یک فرآیند خاص
top                   # نمایش زنده؛ مرتب‌سازی با P (CPU) و M (RAM)
kill -15 4321         # درخواست خروج مؤدبانه (TERM — پیش‌فرض)
kill -9 4321          # قتل فوری (KILL) — آخرین راه‌حل
killall nginx         # کشتن با نام
jobs, fg, bg, &       # مدیریت کارهای پیش‌زمینه و پس‌زمینه
```

- **فرآیند Zombie:** فرآینمی که تمام شده ولی والدش وضعیت خروج را نخوانده؛ در ps با `<defunct>` دیده می‌شود.
- **اولویت:** مقدار nice از ۱۹- تا ۱۹+ است؛ عدد کمتر یعنی اولویت بیشتر. با `nice -n 10 command` اجرا و با `renice` تغییر دهید.
- **سیگنال‌ها:** `TERM` (۱۵) فرصت پاک‌سازی می‌دهد و `KILL` (۹) هسته را وادار می‌کند فرآیند را بلافاصله برکند — برنامه هیچ شانسی ندارد. آزمون همین تفاوت را می‌خواهد.

## systemd و مدیریت سرویس‌ها

توزیع‌های مدرن از **systemd** به‌عنوان init (PID 1) استفاده می‌کنند: سرویس‌ها را بالا می‌آورد، توالی بوت را مدیریت می‌کند و لاگ‌ها را در journal جمع می‌کند. واحد اصلی آن **unit** است؛ رایج‌ترین نوع‌ها `.service` و `.timer` و `.mount`.

```bash
systemctl status ssh          # وضعیت سرویس SSH
sudo systemctl start nginx    # روشن کردن
sudo systemctl stop nginx     # خاموش کردن
sudo systemctl restart nginx  # ری‌استارت کامل
sudo systemctl reload nginx   # بارگذاری مجدد کانفیگ بدون قطع سرویس
systemctl enable ssh          # فعال‌سازی خودکار هنگام بوت
systemctl list-units --type=service --state=running
```

فرق `restart` و `reload` سؤال محبوب آزمون است: restart سرویس را از نو راه می‌اندازد، reload فقط فایل پیکربندی را دوباره می‌خواند و اتصال‌ها را نمی‌بندد.

**سطح‌های بوت (Target):** systemd جایگزین runlevelهای قدیمی شده: `multi-user.target` معادل runlevel 3 (سرور بدون گرافیک) و `graphical.target` معادل runlevel 5. تغییر هدف پیش‌فرض بوت:

```bash
sudo systemctl set-default multi-user.target   # بوت بدون رابط گرافیکی
journalctl -u nginx -f                          # لاگ زنده سرویس nginx
journalctl -b --since "10 min ago"              # لاگ‌های بوت جاری
```

- **فایل unit سفارشی:** سرویس‌های خودتان را در `/etc/systemd/system/myapp.service` تعریف می‌کنید و بعد با `systemctl daemon-reload` به systemd معرفی می‌کنید. سه بخش اصلی فایل: `[Unit]` (توضیح و وابستگی)، `[Service]` (ExecStart و Restart) و `[Install]` (WantedBy).
- **لاگ‌ها:** journalctl جایگزین دستی‌دنبال‌کردن فایل‌های لاگ شده؛ ولی `/var/log/syslog` (دبیان) و `/var/log/messages` (RHEL) هنوز در آزمون سؤال دارند.

## جمع‌بندی

- کاربران در `/etc/passwd` و رمزها در `/etc/shadow`؛ ساخت با `useradd -m` و افزودن به گروه فقط با `usermod -aG`.
- سیاست sudo در `/etc/sudoers` است و ویرایش آن فقط با `visudo` بی‌خطر است.
- فرآیندها PID دارند؛ `top` وضعیت زنده می‌دهد و `kill -15` مؤدبانه می‌خواهد خارج شود ولی `kill -9` فوری و بی‌رحم است.
- systemd با PID=1 سرویس‌ها را مدیریت می‌کند؛ `enable` یعنی اجرای خودکار هنگام بوت و `reload` فقط خواندن مجدد کانفیگ.
- لاگ متمرکز با `journalctl -u سرویس` دیده می‌شود و تارگت‌های بوت جای runlevelهای قدیمی را گرفته‌اند.

برای تمرین: یک سرویس ساده (مثلاً python3 -m http.server 8000) به‌عنوان unit سفارشی تعریف کنید، آن را enable و status بگیرید و با journalctl لاگش را ببینید. این تمرین، ورودی واقعی مسیر LPIC-2 و DevOps است.
